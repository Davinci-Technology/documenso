## Version Policy

Davinci Sign follows [Semantic Versioning](https://semver.org/):

| Version Type | Format  | Description                                |
| ------------ | ------- | ------------------------------------------ |
| Major        | `x.0.0` | Breaking changes, may require manual steps |
| Minor        | `x.y.0` | New features, backward compatible          |
| Patch        | `x.y.z` | Bug fixes, security patches                |

<Callout type="info">
  Review the [release notes](https://github.com/documenso/documenso/releases) before upgrading to
  understand what changes are included.
</Callout>

### Image Tags

| Tag       | Description                      | Use Case             |
| --------- | -------------------------------- | -------------------- |
| `latest`  | Most recent stable release       | Development, testing |
| `x.y.z`   | Specific version (e.g., `1.5.0`) | Production           |
| `release` | Latest build from release branch | Pre-release testing  |

For production deployments, pin to a specific version tag to avoid unexpected updates.

## Backup Before Upgrading

<Callout type="error">
  Always back up your database before upgrading. Upgrades may include database migrations that
  cannot be reversed.
</Callout>

### Database Backup

<Tabs items={['Docker Compose', 'Kubernetes', 'External Database']}>
<Tab value="Docker Compose">

```bash
docker compose exec database pg_dump -U documenso documenso > backup-$(date +%Y%m%d-%H%M%S).sql
```

</Tab>
<Tab value="Kubernetes">

```bash
kubectl exec -n documenso deploy/postgres -- pg_dump -U documenso documenso > backup-$(date +%Y%m%d-%H%M%S).sql
```

</Tab>
<Tab value="External Database">

Use your database provider's backup tools or `pg_dump`:

```bash
pg_dump "postgresql://user:password@host:5432/documenso" > backup-$(date +%Y%m%d-%H%M%S).sql
```

</Tab>
</Tabs>

### Configuration Backup

Back up your environment configuration:

<Tabs items={['Docker / env file', 'Kubernetes']}>
<Tab value="Docker / env file">

```bash
cp .env .env.backup-$(date +%Y%m%d)
```

</Tab>
<Tab value="Kubernetes">

Export your secrets and configmaps:

```bash
kubectl get secret documenso-secrets -n documenso -o yaml > secrets-backup.yaml
kubectl get configmap documenso-config -n documenso -o yaml > configmap-backup.yaml
```

</Tab>
</Tabs>

See [Backups](/docs/self-hosting/maintenance/backups) for automated backup strategies.

## Upgrade Process

### Docker

{/* prettier-ignore */}
<Steps>
<Step>
### Pull the new image

```bash
docker pull davinci/davinci-sign:<version>
```

Replace `<version>` with your target version.

</Step>
<Step>
### Stop the current container

```bash
docker stop documenso
docker rm documenso
```

</Step>
<Step>
### Start with the new image

```bash
docker run -d \
  --name documenso \
  -p 3000:3000 \
  --env-file .env \
  -v /path/to/cert.p12:/opt/davinci-sign/cert.p12:ro \
  davinci/davinci-sign:<version>
```

</Step>
<Step>
### Verify the upgrade

```bash
docker logs -f documenso
```

Wait for "Ready" or "Listening on port 3000" in the output.

Test the health endpoint:

```bash
curl http://localhost:3000/api/health
```

</Step>
</Steps>

### Docker Compose

{/* prettier-ignore */}
<Steps>
<Step>
### Update the image tag

Edit `compose.yml` or your `.env` file to specify the new version:

```yaml
services:
  documenso:
    image: davinci/davinci-sign:<version>
```

Or if using environment variable substitution:

```bash
# In .env
DOCUMENSO_VERSION=<version>
```

```yaml
# In compose.yml
services:
  documenso:
    image: davinci/davinci-sign:${DOCUMENSO_VERSION:-latest}
```

</Step>
<Step>
### Pull the new image

```bash
docker compose pull
```

</Step>
<Step>
### Apply the update

```bash
docker compose --env-file .env up -d
```

Docker Compose recreates containers that have changed images.

</Step>
<Step>
### Verify the upgrade

```bash
docker compose ps
docker compose logs -f documenso
```

Confirm the container is running and healthy.

</Step>
</Steps>

### Kubernetes

{/* prettier-ignore */}
<Steps>
<Step>
### Update the deployment image

Edit the deployment directly:

```bash
kubectl set image deployment/documenso \
  documenso=davinci/davinci-sign:<version> \
  -n documenso
```

Or update your manifest file:

```yaml
spec:
  template:
    spec:
      containers:
        - name: documenso
          image: davinci/davinci-sign:<version>
```

Then apply:

```bash
kubectl apply -f deployment.yaml
```

</Step>
<Step>
### Monitor the rollout

```bash
kubectl rollout status deployment/documenso -n documenso
```

Wait for the rollout to complete.

</Step>
<Step>
### Verify the upgrade

```bash
kubectl get pods -n documenso
kubectl logs -f deployment/documenso -n documenso
```

Confirm pods are running and healthy.

</Step>
</Steps>

### Kubernetes with Helm

{/* prettier-ignore */}
<Steps>
<Step>
### Update values file

Edit your `values.yaml` file:

```yaml
image:
  repository: davinci/davinci-sign
  tag: "<version>"
```

</Step>
<Step>
### Upgrade the release

```bash
helm upgrade documenso . \
  --namespace documenso \
  --values values.yaml \
  --timeout 300s
```

Or if using a remote chart:

```bash
helm upgrade documenso davinci/davinci-sign \
  --namespace documenso \
  --set image.tag=<version> \
  --timeout 300s
```

</Step>
<Step>
### Monitor the upgrade

```bash
helm status documenso -n documenso
kubectl get pods -n documenso -w
```

</Step>
</Steps>

## Migration-Only Updates

For maintenance windows or when running multiple replicas, you may want to run database migrations separately from the application upgrade.

### Run Migrations Separately

```bash
# Run migrations only
docker run --rm \
  -e NEXT_PRIVATE_DATABASE_URL="postgresql://user:password@host:5432/documenso" \
  -e NEXT_PRIVATE_DIRECT_DATABASE_URL="postgresql://user:password@host:5432/documenso" \
  davinci/davinci-sign:<version> \
  npx prisma migrate deploy --schema ../../packages/prisma/schema.prisma
```

<Callout type="warn">
  Ensure no application instances are running when performing migrations to prevent race conditions
  or data corruption.
</Callout>

{/* prettier-ignore */}
<Steps>
<Step>
### Scale down all instances

<Tabs items={['Docker Compose', 'Kubernetes']}>
<Tab value="Docker Compose">

```bash
docker compose stop documenso
```

</Tab>
<Tab value="Kubernetes">

```bash
kubectl scale deployment/documenso --replicas=0 -n documenso
```

</Tab>
</Tabs>

</Step>
<Step>
### Run migrations

```bash
# Run the migration command from above
docker run --rm \
  -e NEXT_PRIVATE_DATABASE_URL="postgresql://user:password@host:5432/documenso" \
  -e NEXT_PRIVATE_DIRECT_DATABASE_URL="postgresql://user:password@host:5432/documenso" \
  davinci/davinci-sign:<version> \
  npx prisma migrate deploy --schema ../../packages/prisma/schema.prisma
```

</Step>
<Step>
### Update application image

Update your compose file or Kubernetes deployment to use the new image version.

</Step>
<Step>
### Scale back up

<Tabs items={['Docker Compose', 'Kubernetes']}>
<Tab value="Docker Compose">

```bash
docker compose up -d documenso
```

</Tab>
<Tab value="Kubernetes">

```bash
kubectl scale deployment/documenso --replicas=2 -n documenso
```

</Tab>
</Tabs>

</Step>
</Steps>

## Rollback

If an upgrade fails or introduces issues, you can rollback to the previous version.

### Quick Rollback

<Tabs items={['Docker', 'Docker Compose', 'Kubernetes']}>
<Tab value="Docker">

```bash
# Stop current container
docker stop documenso
docker rm documenso

# Start with previous image
docker run -d \
  --name documenso \
  -p 3000:3000 \
  --env-file .env \
  -v /path/to/cert.p12:/opt/davinci-sign/cert.p12:ro \
  davinci/davinci-sign:<previous-version>
```

</Tab>
<Tab value="Docker Compose">

```bash
# Edit compose.yml to use previous version
# Then recreate containers
docker compose up -d
```

</Tab>
<Tab value="Kubernetes">

```bash
# Rollback to previous revision
kubectl rollout undo deployment/documenso -n documenso

# Or rollback to specific revision
kubectl rollout history deployment/documenso -n documenso
kubectl rollout undo deployment/documenso --to-revision=<revision> -n documenso
```

</Tab>
</Tabs>

### Database Rollback

<Callout type="error">
  Database migrations typically cannot be automatically reversed. If you need to rollback a
  migration, restore from your database backup.
</Callout>

```bash
# Restore from backup
psql "postgresql://user:password@host:5432/documenso" < backup-YYYYMMDD-HHMMSS.sql
```

## Major Version Upgrades

Major version upgrades may include breaking changes that require additional steps.

<Callout type="warn">
  Always read the release notes for major versions. They may include:

  - Database schema changes
  - Configuration changes
  - API changes
  - Required manual intervention
</Callout>

### Pre-upgrade Checklist

{/* prettier-ignore */}
<Steps>
<Step>
### Review breaking changes

Check the [release notes](https://github.com/documenso/documenso/releases) for breaking changes and required actions.

</Step>
<Step>

</Step>

## Monitoring Upgrades

### Health Checks

After upgrading, monitor these endpoints:

- Health check: `GET /api/health`
- Database status: Check application logs
- Feature functionality: Test key user workflows

### Common Issues

| Issue                    | Symptoms                         | Solution                              |
| ------------------------ | -------------------------------- | ------------------------------------- |
| Migration failure        | App won't start, database errors | Check logs, restore backup if needed  |
| Configuration mismatch   | 500 errors, missing features    | Review env vars against release notes |
| Certificate issues       | SAML/signing errors              | Verify certificate path and format   |
| Resource constraints     | Slow response, timeouts          | Check CPU/memory usage                |

### Log Monitoring

<Tabs items={['Docker', 'Docker Compose', 'Kubernetes']}>
<Tab value="Docker">

```bash
# Follow logs during upgrade
docker logs -f documenso

# Check for errors
docker logs documenso | grep -i error
```

</Tab>
<Tab value="Docker Compose">

```bash

</Tab>

# Check for pod issues
kubectl get events -n documenso --sort-by='.lastTimestamp'
```

</Tab>
</Tabs>

## Automated Upgrades

### Renovate Bot

For automated dependency updates, configure [Renovate](https://docs.renovatebot.com/) in your infrastructure repository:

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:base"],
  "docker": {
    "enabled": true
  },
  "packageRules": [
    {
      "matchPackageNames": ["davinci/davinci-sign"],
      "schedule": ["before 9am on monday"]
    }
  ]
}
```

### Watchtower

For automatic Docker container updates, use [Watchtower](https://containrrr.dev/watchtower/):

```bash
docker run -d \
  --name watchtower \
  -v /var/run/docker.sock:/var/run/docker.sock \
  containrrr/watchtower \
  --schedule "0 0 4 * * *" \
  --cleanup \
  documenso
```

<Callout type="warn">
  Automated upgrades should only be used for patch releases. Always manually review and test major
  and minor releases.
</Callout>

## Best Practices

1. **Pin versions in production**: Use specific version tags, not `latest`
2. **Test upgrades**: Always test in a staging environment first
3. **Backup before upgrading**: Database and configuration backups are essential
4. **Read release notes**: Understand what's changing before upgrading
5. **Monitor after upgrades**: Watch logs and health metrics post-upgrade
6. **Gradual rollouts**: For high-availability setups, upgrade instances gradually
7. **Document your process**: Maintain upgrade procedures for your specific setup
