## Version Policy

Davinci Sign follows [Semantic Versioning](https://semver.org/):

| Version Type | Format  | Description                                |
| ------------ | ------- | ------------------------------------------ |
| Major        | `x.0.0` | Breaking changes, may require manual steps |
| Minor        | `x.y.0` | New features, backward compatible          |
| Patch        | `x.y.z` | Bug fixes, security patches                |

<Callout type="info">
  Review the [release notes](https://github.com/documenso/documenso/releases) before upgrading to
  understand what changes are included.
</Callout>

### Image Tags

| Tag       | Description                      | Use Case             |
| --------- | -------------------------------- | -------------------- |
| `latest`  | Most recent stable release       | Development, testing |
| `x.y.z`   | Specific version (e.g., `1.5.0`) | Production           |
| `release` | Latest build from release branch | Pre-release testing  |

For production deployments, pin to a specific version tag to avoid unexpected updates.

## Checking for Updates

### View Current Version

Check your running Davinci Sign version:

<Tabs items={['Docker', 'Docker Compose', 'Kubernetes']}>
<Tab value="Docker">

```bash
docker inspect documenso --format='{{.Config.Image}}'
```

</Tab>
<Tab value="Docker Compose">

```bash
docker compose images
```

</Tab>
<Tab value="Kubernetes">

```bash
kubectl get deployment documenso -n documenso -o jsonpath='{.spec.template.spec.containers[0].image}'
```

</Tab>
</Tabs>

View available releases on GitHub:

```bash
curl -s https://api.github.com/repos/davinci/davinci-sign/releases/latest | grep tag_name
```

Or visit the [releases page](https://github.com/documenso/documenso/releases).

## Backup Before Upgrading

<Callout type="error">
  Always back up your database before upgrading. Upgrades may include database migrations that
  cannot be reversed.
</Callout>

### Database Backup

<Tabs items={['Docker Compose', 'Kubernetes', 'External Database']}>
<Tab value="Docker Compose">

```bash
docker compose exec database pg_dump -U documenso documenso > backup-$(date +%Y%m%d-%H%M%S).sql
```

</Tab>
<Tab value="Kubernetes">

```bash
kubectl exec -n documenso deploy/postgres -- pg_dump -U documenso documenso > backup-$(date +%Y%m%d-%H%M%S).sql
```

</Tab>
<Tab value="External Database">

Use your database provider's backup tools or `pg_dump`:

```bash
pg_dump "postgresql://user:password@host:5432/documenso" > backup-$(date +%Y%m%d-%H%M%S).sql
```

</Tab>
</Tabs>

### Configuration Backup

Back up your environment configuration:

<Tabs items={['Docker / env file', 'Kubernetes']}>
<Tab value="Docker / env file">

```bash
cp .env .env.backup-$(date +%Y%m%d)
```

</Tab>
<Tab value="Kubernetes">

Export your secrets and configmaps:

```bash
kubectl get secret documenso-secrets -n documenso -o yaml > secrets-backup.yaml
kubectl get configmap documenso-config -n documenso -o yaml > configmap-backup.yaml
```

</Tab>
</Tabs>

See [Backups](/docs/self-hosting/maintenance/backups) for automated backup strategies.

## Upgrade Process

### Docker

{/* prettier-ignore */}
<Steps>
<Step>
### Pull the new image

```bash
docker pull davinci/davinci-sign:<version>
```

Replace `<version>` with your target version.

</Step>
<Step>
### Stop the current container

```bash
docker stop documenso
docker rm documenso
```

</Step>
<Step>
### Start with the new image

```bash
docker run -d \
  --name documenso \
  -p 3000:3000 \
  --env-file .env \
  -v /path/to/cert.p12:/opt/davinci-sign/cert.p12:ro \
  davinci/davinci-sign:<version>
```

</Step>
<Step>
### Verify the upgrade

```bash
docker logs -f documenso
```

Wait for "Ready" or "Listening on port 3000" in the output.

Test the health endpoint:

```bash
curl http://localhost:3000/api/health
```

</Step>
</Steps>

### Docker Compose

{/* prettier-ignore */}
<Steps>
<Step>
### Update the image tag

Edit `compose.yml` or your `.env` file to specify the new version:

```yaml
services:
  documenso:
    image: davinci/davinci-sign:<version>
```

Or if using environment variable substitution:

```bash
# In .env
DOCUMENSO_VERSION=<version>
```

```yaml
# In compose.yml
services:
  documenso:
    image: davinci/davinci-sign:${DOCUMENSO_VERSION:-latest}
```

</Step>
<Step>
### Pull the new image

```bash
docker compose pull
```

</Step>
<Step>
### Apply the update

```bash
docker compose --env-file .env up -d
```

Docker Compose recreates containers that have changed images.

</Step>
<Step>
### Verify the upgrade

```bash
docker compose ps
docker compose logs -f documenso
```

Confirm the container is running and healthy.

</Step>
</Steps>

### Kubernetes

{/* prettier-ignore */}
<Steps>
<Step>
### Update the deployment image

Edit the deployment directly:

```bash
kubectl set image deployment/documenso \
  documenso=davinci/davinci-sign:<version> \
  -n documenso
```

Or update your manifest file:

```yaml
spec:
  template:
    spec:
      containers:
        - name: documenso
          image: davinci/davinci-sign:<version>
```

Then apply:

```bash
kubectl apply -f documenso-deployment.yaml
```

</Step>
<Step>
### Monitor the rollout

```bash
kubectl rollout status deployment/documenso -n documenso
```

The rollout completes when all pods are running the new version.

</Step>
<Step>
### Verify the upgrade

```bash
kubectl get pods -n documenso
kubectl logs -f deployment/documenso -n documenso
```

Test the application externally once the pods are ready.

</Step>
</Steps>

## Database Migrations

Database migrations run automatically when Davinci Sign starts up. However, for high-traffic deployments or during major upgrades, you may want to run migrations separately:

### Running Migrations Separately

{/* prettier-ignore */}
<Steps>
<Step>
### Stop the application

Stop Davinci Sign to prevent concurrent database access during migration.

</Step>
<Step>
### Run migrations

<Tabs items={['Docker', 'Docker Compose', 'Kubernetes']}>
<Tab value="Docker">

```bash
# Run migrations only
docker run --rm \
  -e NEXT_PRIVATE_DATABASE_URL="postgresql://user:password@host:5432/documenso" \
  -e NEXT_PRIVATE_DIRECT_DATABASE_URL="postgresql://user:password@host:5432/documenso" \
  davinci/davinci-sign:<version> \
  npx prisma migrate deploy --schema ../../packages/prisma/schema.prisma
```

</Tab>
<Tab value="Docker Compose">

Add a migration service to your `compose.yml`:

```yaml
services:
  migrate:
    image: davinci/davinci-sign:<version>
    profiles: ["tools"]
    environment:
      NEXT_PRIVATE_DATABASE_URL: ${DATABASE_URL}
      NEXT_PRIVATE_DIRECT_DATABASE_URL: ${DATABASE_URL}
    command: npx prisma migrate deploy --schema ../../packages/prisma/schema.prisma
    depends_on:
      - database
```

Run migrations:

```bash
docker compose --profile tools run --rm migrate
```

</Tab>
<Tab value="Kubernetes">

Create a migration job:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: documenso-migrate
  namespace: documenso
spec:
  template:
    spec:
      containers:
        - name: migrate
          image: davinci/davinci-sign:<version>
          envFrom:
            - secretRef:
                name: documenso-secrets
          command:
            - npx
            - prisma
            - migrate
            - deploy
            - --schema
            - ../../packages/prisma/schema.prisma
      restartPolicy: Never
  backoffLimit: 3
```

Apply and monitor:

```bash
kubectl apply -f migrate-job.yaml
kubectl wait --for=condition=complete job/documenso-migrate -n documenso
```

</Tab>
</Tabs>

</Step>
<Step>
### Restart the application

Start Davinci Sign again after migrations complete successfully.

</Step>
</Steps>

<Callout type="warn">
  Always test database migrations on a copy of your production data before running them in production.
</Callout>

## Breaking Changes

Some releases may include breaking changes that require manual intervention:

### Major Version Upgrades

1. **Review the migration guide** - Check the release notes for specific upgrade instructions
2. **Test in staging** - Run the upgrade process in a test environment first
3. **Plan downtime** - Some migrations may require extended downtime
4. **Update configuration** - Environment variables or settings may have changed

### Common Breaking Changes

- Database schema changes requiring manual migration steps
- Configuration file format changes
- API endpoint changes (if using REST API)
- Docker container startup command changes

## Rollback Procedures

If an upgrade fails, you can rollback using these procedures:

### Database Rollback

Restore from the backup created before upgrade:

<Tabs items={['Docker Compose', 'Kubernetes', 'External Database']}>
<Tab value="Docker Compose">

```bash
# Stop the application
docker compose down

# Restore database
docker compose exec database psql -U documenso -c "DROP DATABASE IF EXISTS documenso;"
docker compose exec database psql -U documenso -c "CREATE DATABASE documenso;"
docker compose exec -T database psql -U documenso -d documenso < backup-YYYYMMDD-HHMMSS.sql

# Start with previous version
docker compose up -d
```

</Tab>
<Tab value="Kubernetes">

```bash
# Scale down deployment
kubectl scale deployment documenso --replicas=0 -n documenso

# Restore database (example for PostgreSQL pod)
kubectl exec -n documenso deploy/postgres -- dropdb -U documenso documenso
kubectl exec -n documenso deploy/postgres -- createdb -U documenso documenso
kubectl exec -i -n documenso deploy/postgres -- psql -U documenso -d documenso < backup-YYYYMMDD-HHMMSS.sql

# Update to previous image
kubectl set image deployment/documenso documenso=davinci/davinci-sign:<previous-version> -n documenso
kubectl scale deployment documenso --replicas=1 -n documenso
```

</Tab>
<Tab value="External Database">

Use your database provider's restore tools or:

```bash
# Drop and recreate database
dropdb "postgresql://user:password@host:5432/documenso"
createdb "postgresql://user:password@host:5432/documenso"
psql "postgresql://user:password@host:5432/documenso" < backup-YYYYMMDD-HHMMSS.sql
```

</Tab>
</Tabs>

### Application Rollback

Revert to the previous container image:

<Tabs items={['Docker', 'Docker Compose', 'Kubernetes']}>
<Tab value="Docker">

```bash
docker stop documenso
docker rm documenso

# Start with previous version
docker run -d \
  --name documenso \
  -p 3000:3000 \
  --env-file .env \
  -v /path/to/cert.p12:/opt/davinci-sign/cert.p12:ro \
  davinci/davinci-sign:<previous-version>
```

</Tab>
<Tab value="Docker Compose">

Update your compose file to use the previous version:

```yaml
services:
  documenso:
    image: davinci/davinci-sign:<previous-version>
```

Then restart:

```bash
docker compose up -d
```

</Tab>
<Tab value="Kubernetes">

```bash
kubectl set image deployment/documenso \
  documenso=davinci/davinci-sign:<previous-version> \
  -n documenso

kubectl rollout status deployment/documenso -n documenso
```

</Tab>
</Tabs>

## Post-Upgrade Verification

After upgrading, verify that everything is working correctly:

### Health Checks

1. **Application Health**:
   ```bash
   curl http://localhost:3000/api/health
   ```

2. **Database Connectivity**:
   Check application logs for database connection messages.

3. **Email Functionality**:
   Test sending a document to ensure email integration works.

### Functional Testing

1. **Sign In** - Verify user authentication works
2. **Upload Document** - Test document upload functionality
3. **Send for Signing** - Create and send a test document
4. **Sign Document** - Complete the signing process
5. **Download** - Verify completed documents can be downloaded

### Performance Monitoring

Monitor key metrics after upgrade:

- Response times
- Memory usage
- CPU utilization
- Database query performance
- Error rates in logs

## Automation

For production environments, consider automating upgrades:

### CI/CD Pipeline

Example GitHub Actions workflow:

```yaml
name: Automated Upgrade

on:
  schedule:
    - cron: "0 2 * * 1" # Weekly on Monday at 2 AM
  workflow_dispatch:

jobs:
  upgrade:
    runs-on: ubuntu-latest
    steps:
      - name: Backup Database
        run: |
          # Backup commands here
          
      - name: Deploy New Version
        run: |
          # Deployment commands here
          
      - name: Verify Health
        run: |
          curl -f http://your-documenso-instance/api/health
          
      - name: Notify Team
        if: failure()
        run: |
          # Send notification on failure
```

### Update Notifications

Set up monitoring for new releases:

```bash
#!/bin/bash
# check-updates.sh

CURRENT_VERSION=$(curl -s https://your-documenso-instance/api/health | jq -r '.version')
LATEST_VERSION=$(curl -s https://api.github.com/repos/davinci/davinci-sign/releases/latest | jq -r '.tag_name')

if [ "$CURRENT_VERSION" != "$LATEST_VERSION" ]; then
    echo "New version available: $LATEST_VERSION (current: $CURRENT_VERSION)"
    # Send notification
fi
```

Run this script periodically via cron to get notified of updates.

## Troubleshooting

### Common Upgrade Issues

<Accordions>
<Accordion title="Migration Timeout">

If database migrations are taking too long:

1. Check available disk space
2. Monitor database connections and locks
3. Consider running migrations manually during maintenance window
4. Increase migration timeout if configurable

</Accordion>
<Accordion title="Container Won't Start">

If the new container fails to start:

1. Check the container logs: `docker logs documenso`
2. Verify environment variables are correct
3. Ensure file permissions are correct for mounted volumes
4. Check if ports are already in use

</Accordion>
<Accordion title="Database Connection Issues">

If you see database connection errors:

1. Verify `NEXT_PRIVATE_DATABASE_URL` is correct
2. Check if database is running and accessible
3. Ensure firewall allows database connections
4. Verify database user permissions

</Accordion>
<Accordion title="Email Issues After Upgrade">

If email functionality stops working:

1. Check SMTP configuration hasn't changed
2. Verify environment variables for email settings
3. Test SMTP connectivity from the container
4. Check email service logs for authentication issues

</Accordion>
</Accordions>

### Getting Help

If you encounter issues during upgrade:

1. **Check Logs** - Always start with container/pod logs
2. **Review Documentation** - Check the [troubleshooting guide](/docs/self-hosting/troubleshooting)
3. **Search Issues** - Look for similar problems in [GitHub issues](https://github.com/documenso/documenso/issues)
4. **Community Support** - Ask for help in the [Discord community](https://davincisolutions.ai/discord)
5. **Create Issue** - If you find a bug, [report it](https://github.com/documenso/documenso/issues/new)

Remember to include:
- Current version
- Target version
- Deployment method (Docker, Docker Compose, Kubernetes)
- Error messages
- Relevant configuration (anonymized)
